## 1. 推荐拓扑与管理端部署

本次PG全面统一的运维增量：开发/CI/staging/生产使用独立PG环境与权限，API/Worker/管理/维护统一PG；迁移由单一受控执行者在线运行，锁覆盖多主机入口。备份/恢复只针对PG，旧SQLite备份timer退出正式部署。历史导入工具作为独立operator制品/一次性作业，不进入客户或API/Worker运行包，按CW-060保护封存源与工作副本。

CW-056必须覆盖空库及每个实际支持旧PG head带代表数据升级；CW-033先实际restore隔离副本，CW-048再验证PITR/RTO/RPO；逻辑快照不能冒充PITR。生产切换或代码回退后业务真源保持PG，SQLite仅归档/历史输入。下列旧部署命令是当前实现基线，最终唯一制品和命令由CW-032/044按同一SHA重新核验。

管理端不是单独的后端服务，但自 CW-019 起是**单独的前端构建制品**。两类制品
的归属与产出命令如下（同一发布 SHA 下产出，两者不得混用目录）：

| 制品 | 产出命令（仓库根） | 输出目录 | 部署归属 |
|---|---|---|---|
| 客户工作台 | `npm run build`（或 `npm run build:all` 的客户半段） | `client/dist` | 随 Tauri 双包（`frontendDist: "../dist"`）与客户 Nginx `root` |
| 管理控制台 | `npm run build:admin` | `client/dist-admin` | 只随服务器部署，Nginx `location ^~ /admin/` `alias` 到该目录；内部 P0 侧保留内网 `allow` + `deny all` + Basic Auth |

一次产出两者用 `npm run build:all`；产出后必须跑 `npm run verify:customer-bundle`
（CI 同名 step），它断言 `client/dist` 内不含 `admin.html`、`admin-main*`、任何
名字含 `admin` 的 chunk，以及 `AdminApp`、`/api/control/`、`激活码批次`、`审计中心`、
`强制下线` 等管理域特征串，任一命中即退出 1。

两类制品仍部署在同一 HTTPS origin 下：Nginx 提供静态文件，`/api/*` 转发给无状态
FastAPI。这样 ASX1 管理员交换凭据只进入 HttpOnly cookie，浏览器配合 CSRF header
使用，任何管理员 secret 都不写入前端存储。管理制品的 `base` 为 `/admin/`，因此
不能用 `file://` 或站点根路径直接打开（资源路径带 `/admin/` 前缀，会 404）。

类生产最小拓扑如下：

- 一个受控 TLS/LB 入口，使用 `deploy/nginx/customer.conf.example`；
- 对外 origin 固定标准 HTTPS 443 端口，不支持非标准端口；
- `video-replica-api@8001` 与 `video-replica-api@8002` 两个独立 API 进程；
- `video-replica-worker@1` 至 `video-replica-worker@4` 四个独立 Worker；
- PostgreSQL 16 HA 的唯一读写主端点；
- 一个私有 COS bucket，禁止公开读，短期签名 URL 只由服务端生成；
- 一个 maintenance timer 实例，避免多节点重复扫表；
- 集中日志、指标和 P1 告警由 T37 接入。

在一台机器运行上述进程只用于验证模板和进程级并发，不足以证明主机故障
隔离。正式 `STAGING_VERIFIED` 证据必须写明 API/Worker 所在故障域、LB
后端成员和节点替换记录，不能用单 API/单 Worker 健康检查冒充多实例。

## 2. 首次安装

1. 在候选发布 SHA 构建 Web 静态文件：`npm run build:all` 一次产出客户制品
   `client/dist` 与管理制品 `client/dist-admin`，随后 `npm run verify:customer-bundle`
   必须退出 0。将两者只读部署到 `/opt/video-replica/app/client/dist` 与
   `/opt/video-replica/app/client/dist-admin`（Nginx `alias` 路径见第 1 节与
   `deploy/nginx/customer.conf.example`）。
2. 安装 `ffmpeg` 系统包并确认 `/usr/bin/ffprobe` 可执行；视频上传预检和成片
   音轨质检都依赖该二进制，API 与 Worker 的 systemd 模板会在启动前显式检查，
   缺失时拒绝接流量。随后创建专用 `video-replica` 系统用户，将代码与
   `server/.venv` 部署到 `/opt/video-replica/app`；该用户不拥有
   `/etc/video-replica/customer.env`。Debian/Ubuntu 主机可执行：

   ```bash
   apt-get update
   apt-get install -y --no-install-recommends ffmpeg
   test -x /usr/bin/ffprobe
   ```
3. 复制 `deploy/customer.env.example` 到 `/etc/video-replica/customer.env`，
   权限设为 root 可写、服务组只读。真实 DSN、HMAC/AEAD/Fernet 密钥不得进
   Git、工单、截图或 shell history。

   T45 起，迁移和每次生产重启前都必须先运行身份/指标红线预检。该命令只输出
   变量名和文件元数据结论，不输出任何密钥或 token：

   ```bash
   /opt/video-replica/app/server/.venv/bin/python \
     /opt/video-replica/app/scripts/customer_release_preflight.py \
     --env-file /etc/video-replica/customer.env \
     --service-user video-replica
   ```

   只有出现 `T45_PREFLIGHT_OK` 才能继续。开发身份模式、开发身份请求头、桌面
   身份、相对或缺失的 metrics token 文件、短 token、非普通文件、非服务账号
   owner，或 token 对 group/other 开放权限，都会 fail closed。生产 systemd 的
   `ExecStartPre` 应固定加入同一命令，避免手工检查通过后配置又漂移。
4. 在 PostgreSQL 私网创建最小权限应用角色；所有进程使用同一 HA 主端点。
   将服务商/私有 CA 证书只读部署到 `/etc/video-replica/postgresql-ca.pem`，DSN
   使用 `sslmode=verify-full&sslrootcert=...`。客户生产启动门会拒绝缺失
   `sslmode` 以及 `disable/allow/prefer`，不得依赖 libpq 默认降级策略。
5. 在唯一指定迁移主机加载 customer env 后运行
   `deploy/postgres/migrate.sh`。它用本机 `flock` 阻止同主机并发迁移；禁止
   多主机同时执行。脚本在 Alembic 前复用客户数据库启动门，SQLite、缺失
   `sslmode` 或 `disable/allow/prefer` 会在任何迁移语句前失败。
6. 在打开 API/Worker 客户生产启动门前配置可追溯管理员与私有 COS：
   - 推荐路径是 T07 导入已经包含 active admin 与加密 COS 配置的内部库；导入后
     核对 `active_storage_provider=cos`。
   - 对迁移完成且仍处于原始状态的新库，先创建 root-only（`0600`）的临时 JSON，
     只含 `access_key_id`、`secret_access_key`、`bucket`、`region` 四项；加载
     customer env 后执行：

     ```bash
     umask 077
     install -d -m 0700 -o root -g root /run/video-replica
     /opt/video-replica/app/server/.venv/bin/python -m app.bootstrap \
       provision-empty-customer --confirm-empty-database \
       --admin-username first-admin --admin-display-name "First Admin" \
       --cos-config-file /etc/video-replica/cos-bootstrap.json \
       > /run/video-replica/first-admin-exchange.json
     ```

     该 one-shot 命令用数据库 advisory lock + SERIALIZABLE 事务原子创建首位 admin、
     空钱包、加密 COS 配置、runtime 选择和无 secret 审计；数据库已有用户、
     provider settings、审计记录，或 runtime settings 已由操作者更新时均拒绝。
     输出只含 admin id 与 15 分钟、单次使用的 exchange credential，必须
     立即转入密码管理器并安全删除临时输入/输出文件，不得进入日志、工单或
     shell history。`/run` 每次重启都会清空，所以必须在重定向前显式创建上述
     root-only 目录，不能假设它已存在。命令不调用 COS；随后正式 bootstrap 的
     bucket HEAD 才是连通性门。

   不得在空库上先启动临时控制面，也不得把 legacy/dev 身份写入 `customer.env`。
   没有私有 COS 授权时此步骤保持阻塞，不能绕过启动门。
7. 安装两个 systemd 模板、maintenance service/timer 与 T38 的 PostgreSQL PITR
   base-backup service/timer，执行 daemon-reload。客户 PostgreSQL 不得安装旧的
   `video-replica-backup.timer`（它仅适用于内部 SQLite P0）。
8. 启动 `video-replica-api@8001`、`video-replica-api@8002`，再独立启动
   `video-replica-worker@1`、`video-replica-worker@2`、
   `video-replica-worker@3`、`video-replica-worker@4`。
9. 替换 Nginx 示例域名与证书路径，检查配置后 reload。Uvicorn 命令必须
   保留 `--no-proxy-headers`；最后一跳 Nginx 必须覆盖而不是追加 Host、
   X-Forwarded-Proto 和单值 X-Forwarded-For。

### 2.1 管理员首次密码设置（迁移 043 起）

`043_admin_password_login` 不会为已有管理员生成默认密码。发布迁移完成后，
在已加载 customer env 的受控主机进入 `server/`，为目标 active admin 签发一个
15 分钟、单次使用的恢复凭据：

```bash
uv run python -m scripts.issue_admin_exchange_credential \
  --actor-user-id <active-admin-user-id> --ttl-seconds 900
```

命令输出的 `ASX1` 凭据只能进入受控密码管理器，不能进入聊天、日志、工单或
shell history。管理员随后访问同源 `/admin`，选择“首次设置或找回密码”，交换该
凭据并设置 12–128 字符的新密码；保存会撤销该管理员全部旧会话，之后使用账号密码
日常登录。忘记密码时重复这一恢复流程，不得在数据库中手工写入密码摘要。

## 3. 健康检查

- `GET /live` 只证明 API 进程能响应，不访问数据库或 COS。
- `GET /ready` 在客户模式复查 PostgreSQL round-trip、共享设置解密、
  `active_storage_provider=cos` 和 COS 必填配置；任何失败返回 503。
- 同机 Nginx 对 `/live`、`/ready` 使用 operational-only 的 `127.0.0.2` 转发
  哨兵，避免本机监控地址与 Nginx→Uvicorn 回环 peer 相同而触发防重写门；业务
  `/api/` 仍必须传真实 `$remote_addr`，不得复用该哨兵。
- systemd 先检查 `/usr/bin/ffprobe`，再由 `ExecStartPre=python -m app.bootstrap`
  执行同一启动门。缺媒体检测工具、PG、私有 COS 或安全配置时 API/Worker
  都拒绝进入运行状态。

LB 只能把 `/ready` 为 200 的 API 纳入流量。仓库 Nginx 模板把
`http_503` 计为 upstream 失败且 `max_fails=1`，一次失败探测便将该
API 摘除 30 秒，upstream `zone` 使失败状态在所有 Nginx worker 间
共享；同机监控必须持续访问该私有端点。`/ready` 默认仅
允许 loopback；若监控在独立私网，只可替换为其精确 CIDR，不得向公网
开放重型 PG/COS 探测。不得因为 `/live` 为 200 就开放业务流量；
`/live=200,/ready=503` 的含义是“进程活着但依赖不可用”。

## 4. T37 日志、指标与 P1 告警

### 4.1 结构化日志

API 的 HTTP 完成日志输出单行 JSON，固定包含 `request_id`、`operation`、
`method`、路由模板、HTTP 状态、业务结果码和耗时；仅在当前操作已知时附加
actor/user/device/session epoch/task/order/激活码掩码。禁止把请求体、Authorization、
设备/session token、完整激活码、签名 URL、Provider 原始响应或任意字典塞入日志。
两个 API 的 journal 必须进入同一集中日志平台，并以 `request_id` 作为首要检索键。
未知 HTTP 扩展方法在指标中统一归入 `OTHER`，未匹配路径统一归入 `UNMATCHED`；
日志仍保留实际方法和请求路径模板，不能用攻击者输入扩张 Prometheus 标签。

管理端仍按第 1 节部署：它是独立构建制品 `client/dist-admin`，由 Nginx
`location ^~ /admin/` 以 `alias` 提供，与客户站点同源，不单独启动
“管理端服务器”。Nginx 同时提供静态页面并把 `/api/*` 转发给两个 FastAPI；
管理员 exchange credential 只用于换取 HttpOnly cookie，不写入 Web 存储或日志。

### 4.2 双 API 指标抓取

在 API 主机创建独立于 release 目录的高熵 Bearer 文件；不要把 token 放进 env、
命令行参数、Prometheus 配置正文或 Git：

```bash
umask 077
install -d -m 0750 -o root -g video-replica /etc/video-replica
openssl rand -base64 48 > /etc/video-replica/metrics.token
chown video-replica:video-replica /etc/video-replica/metrics.token
chmod 0600 /etc/video-replica/metrics.token
```

`customer.env` 只配置文件路径
`VIDEO_REPLICA_METRICS_TOKEN_FILE=/etc/video-replica/metrics.token`。同机 collector
分别抓取 `/internal/metrics/api-1` 与 `/internal/metrics/api-2`，不能只抓 LB 聚合
入口，否则会漏掉单进程异常。路径仅允许 loopback，抓取时仍须使用正式域名、
正确 TLS SNI/Host 和 Bearer token file；可在该主机用受控本地 DNS/hosts 将正式
域名解析到 loopback，不得改成额外公开 metrics 域名或绕过 Host 校验。

当前 exporter 是进程本地 HTTP/fencing/ready 指标。PostgreSQL 连接、慢查询、
复制延迟与备份/PITR 需要目标环境的数据库监控角色和备份平台，在 T38/T39
另行接入；不要给应用角色授予 `pg_monitor`，也不得把“无这些指标”写成已验收。

### 4.3 单所有者集群异常探针

在且只在一个指定 OPS 主机安装并启用 timer；脚本的 PostgreSQL transaction
advisory lock 是误启第二实例时的第二道拒绝门：

```bash
install -m 0644 deploy/systemd/video-replica-ops-alerts.service /etc/systemd/system/
install -m 0644 deploy/systemd/video-replica-ops-alerts.timer /etc/systemd/system/
systemctl daemon-reload
systemctl start video-replica-ops-alerts.service
systemctl enable --now video-replica-ops-alerts.timer
systemctl list-timers video-replica-ops-alerts.timer
```

首次手动运行必须在迁移 042 完成后成功。探针每分钟执行有界查询，状态由
PostgreSQL 的 `ops_alert_state` 跨 OPS 主机共享；session advisory lock 覆盖查询
事务提交、全部边沿输出和共享状态确认，错峰误启的第二主机也不会独立重发。
只有全部输出成功后才推进状态，输出失败则下次重试。只在状态边沿向 journal 输出
`fired`/`resolved` JSON，内容只有固定 alert 名、严重度、时间和数量。集中日志/
告警平台必须把所有 `fired`、探针 unit 失败、timer 漏执行升级为 P1，并把
`resolved` 关联到原事件。开放灰度前必须注入至少一项可回滚异常，保存外部接收
时间与恢复通知；只有本地 journal 或静态合同测试时 OPS-02 仍保持部分完成。

固定告警面共 11 类：同 epoch 双设备在线或新 epoch LOGIN 后旧 epoch heartbeat、重复 CHARGE、重复 provider trade no、
PAID 无 CHARGE、CHARGE 来源/金额/用户不一致、钱包与流水不一致、旧 session 写入
被拒绝、旧 session 写入实际提交、跨用户访问（成功越权摘要或拒绝审计）、队列饥饿、终态任务悬挂
reserve。迁移 042 为每个 session/epoch 组合最多保留一条成功提交的 expected/
verified epoch 摘要事实；两者不一致即持续触发 `stale_write_committed` P1。该事实与
业务写在同一事务提交，不含用户、设备或 session 明文，并由 append-only 触发器
禁止更新、删除和清空。存在事实时 042 downgrade 会 fail closed，回滚前须人工
导出并保留审计链。

历史业务表的 `created_at` 是 `TEXT`，且 PostgreSQL 会按写入连接的时区渲染
`CURRENT_TIMESTAMP`。042 在迁移事务中按 UTC 一次回填、并维护可索引的 absolute-time
companion 列；探针只查询这些 typed 列，禁止把 UTC 字符串按字典序比较或在探针中对
TEXT 列逐行强转。队列饥饿从超时 PENDING/QUEUED 任务出发再 left join 游标，因此没有
游标和有空闲游标的用户都会被发现；维护清理器不得删除仍有待办任务的游标。

同一 revision 还为 PostgreSQL 项目及其归属资产的非管理 owner 判定保留
`customer_authorization_evidence` 摘要对。正常拒绝时候选行随业务事务回滚，并由
独立拒绝审计继续覆盖；若 owner 判定回归而让 actor≠owner 的操作提交，该不相等
摘要对会成为 append-only `cross_user_access` P1 事实。正常 owner 成功对按资源
类型和摘要对去重，表中不保存 raw user id；非空时同样禁止 042 降级。

## 5. T38 PostgreSQL PITR 与恢复演练

本节先只交付可审计的脚本与演练方法。必须使用 PostgreSQL 16 的物理
`pg_basebackup` 和连续归档 WAL；`pg_dump`、应用导出或“有一个备份文件”都不能
替代 PITR。真实 archive helper、异地副本、受控 staging 主机和数据库角色准备好前，
本任务只能是 `AUTOMATED_VERIFIED`。

1. 由数据库管理员在私有 primary 配置 `wal_level=replica`（或 `logical`）、
   `archive_mode=on`（或 `always`）及 `archive_command` 或 `archive_library`。把
   backup libpq service file、密码来源与 archive helper 放在受控文件中；应用的
   `VIDEO_REPLICA_DATABASE_URL` 绝不复用于物理备份。
2. 在唯一 OPS 主机创建 `/var/lib/video-replica-pitr/backups` 与
   `/var/lib/video-replica-pitr/recovery`（`postgres:postgres`、`0700`），安装
   `video-replica-pitr-backup.service/timer`，该服务**只**加载 root:postgres `0640`
   的 `/etc/video-replica/pitr.env`，不得加载 `customer.env`，以免应用 DSN 或
   应用密钥进入备份进程。archive helper 必须实现
   `put-wal`、`assert-wal`、`put-base`、`assert-base`、`get-base`、`get-wal`，并让
   `assert-*` 只在异地副本真实可取后成功。
   PostgreSQL 的 `archive_command`（或等价 archive library）必须把已引用的
   `%p` 与 `%f` 交给 `put-wal`；timeline 的八位十六进制 `.history` 文件也必须
   原样保存。
3. 首次运行 `deploy/postgres/pitr-preflight.sh`。它会强制切换一个 WAL 并轮询
   `assert-wal`；未能从异地副本取回时立即停止，不允许开始 base backup。
4. 启动一次 `deploy/postgres/pitr-backup.sh`，记录生成的 label、开始/结束时间、
   `pg_verifybackup` 成功和 `assert-base` 成功。正常日常调度由 PITR timer 完成。
5. 在**该 base backup 之后**，仅向隔离 staging 写入恰好 100 条合成的、互不重复的
   activation → recharge order → `CHARGE` → session epoch 关联事实。以 `postgres` 身份
   用 **同一份专用 backup service** 执行（将 service file/name 替换成受控
   `/etc/video-replica/pitr.env` 中的实际值，不能使用 application DSN）：
   `cd /opt/video-replica/app/server && sudo -u postgres env \
   VIDEO_REPLICA_PG_BACKUP_SERVICE_FILE=/etc/video-replica/backup.pg_service.conf \
   VIDEO_REPLICA_PG_BACKUP_SERVICE=video_replica_pitr \
   python -m scripts.pitr_recovery_facts capture --not-before BASE_BACKUP_COMPLETED_UTC \
   --manifest /受控路径/label.json`。CLI 会强制把这两个受控变量转换为 libpq 的
   `PGSERVICEFILE`/`PGSERVICE`，覆盖任何继承的默认连接；`--not-before` 必须是该 base
   backup 完成后立即记录的 UTC 时刻；不足 100 条此后的事实即拒绝。manifest 只允许
   `0600`，不得进入证据仓库或日志。
6. 恢复主机必须与 production 隔离，且只恢复合成 staging 数据。显式设置
   `VIDEO_REPLICA_PITR_DRILL_ENV=staging` 和
   `VIDEO_REPLICA_PITR_DRILL_CONFIRM=RESTORE_SYNTHETIC_STAGING_DATA`，再运行
   `deploy/postgres/pitr-restore-drill.sh --label LABEL --manifest /绝对路径/label.json`。
   脚本只在指定 recovery root 下删除同 label 的旧演练目录，拉取 base 后执行
   `pg_verifybackup`，写入 `recovery.signal` 与 `restore_command`，在隔离端口完成
   `recovery_target_time` 的 WAL 重放并提升。
7. 脚本会对恢复实例运行 `pitr_recovery_facts verify`；只有 100 条 activation、order、
   `CHARGE`、user 和 session epoch **逐笔完全一致**时才成功。记录 RPO（目标时刻
   与最后事务的差）和 RTO（开始恢复至逐笔验证通过），以及 SHA、label、manifest
   digest、WAL/base 的异地取回记录；不记录真实 ID、DSN、密码、token 或对象 URL。
8. 任一 `assert-*`、校验、提升或 100 条核对失败时，停止演练并保留失败时间线；不得
   将“备份存在”标为通过。修复后从新的 label 重演。生产恢复、切换或真实客户数据
   操作不在本任务授权范围内。

## 6. T36 类生产验收

证据必须绑定同一候选 SHA，并至少记录：

1. 两个 API 都被 LB 命中；逐个停止后业务请求仍成功，再恢复成员。
2. 四个 Worker 使用唯一 worker id，公平队列任务无重复领取；逐个 kill/restart
   后租约与提交不确定状态符合 T26。
3. 两个不同客户端 IP 经代理后进入不同的 PostgreSQL 限流桶；伪造多值 XFF、
   错 Host、HTTP proto 和绕过 LB 的请求都被拒绝。
4. PostgreSQL HA 主备切换期间 `/ready` 摘除不健康 API；恢复后无双在线、
   重复入账、旧 session 写入或队列失序。
5. 私有 COS 禁止匿名读，并完成最小权限 put/head/get/copy/archive/delete 证据。
   真实 COS 操作需要用户授权；完整归档联合链在 T40 关闭。
6. 客户云 Windows 构建是唯一默认目标：`npm run tauri:build`（保留别名
   `npm run tauri:build:customer`）以 `--no-default-features` 编译并叠加
   `tauri.customer.conf.json`。客户版的 product name、application identifier、
   publisher、开始菜单目录、HTTPS-only CSP 与空 `bundle.resources` 全部由 base
   `tauri.conf.json` 承载；`tauri.customer.conf.json` 只追加发行专属的
   `installerHooks`。因为 base 的 `bundle.resources` 为空、默认 feature 集不含
   `local-sidecar`，客户安装包不会放入内部版 `start-backend.bat/.sh`，也不得与
   内部版共用安装/升级身份。
   构建环境把 `VITE_API_BASE_URL` 设为与客户服务相同的 HTTPS origin；缺失或
   不是纯 HTTPS origin 时构建会失败。内部版降级为显式 opt-in：只有
   `npm run tauri:build:internal`（`--config tauri.internal.conf.json
   --features local-sidecar`）才启用本地 sidecar；`Cargo.toml` 的 `default = []`
   保证任何未显式加 `--features local-sidecar` 的构建都不会打进本地启动器。
   CI 以 `check:tauri` 默认校验客户版配置、`check:tauri:internal` 校验内部
   opt-in 目标；打包先构建并归档内部版 NSIS，隔离其产物后再独立构建、解包客户
   NSIS 并拒绝本地启动脚本；`.invalid` 地址只用于验证无 sidecar 构建合同，对应
   未签名产物只能标记 `UNSIGNED_INTERNAL_TEST`，不得拿去联调。

没有真实服务器、域名/TLS、PG HA 和私有 COS 时，本节只能保留为待执行清单，
证据层级停在 `AUTOMATED_VERIFIED`。

### 6.1 T39 staging 故障演练

本节是**真实类生产 staging** 的一次性操作单，而不是可在开发机、CI 或 production
直接执行的脚本。演练前由 OPS 固定同一候选 SHA、配置版本、Alembic head、LB 地址和
回滚 SHA，并在证据包中记录开始时间。未完成 T36 的双 API/四 Worker/PG HA 部署，或
未取得该 staging 窗口的 OPS 授权时，停止在 `AUTOMATED_VERIFIED`；不得将此清单
标为 `STAGING_VERIFIED`。

1. **基线与停止规则**：确认 `video-replica-api@8001`、
   `video-replica-api@8002`、`video-replica-worker@1` 至
   `video-replica-worker@4` 全部运行，LB 只转发 `/ready=200` 成员，T37 探针无
   未解释 P1。预先建立两设备单在线、一个可恢复 worker lease、一个仅合成数据的
   100 条 activation/order/`CHARGE`/session epoch manifest。任何双在线、重复
   `CHARGE`、重复 Provider 提交、钱包与账本差额、旧 epoch 成功写入或队列重复领取
   都是立即停止、从 LB 摘除变更并按第 8 节回滚的 No-Go；禁止直接改余额或删除账本。
2. **API 进程故障**：一次只注入一个成员，例如在受控 staging 主机执行
   `systemctl kill --kill-who=main --signal=SIGKILL video-replica-api@8001`，持续从
   LB 以已绑定的两设备会话发起无副作用验证，并记录故障开始、LB 摘除、另一 API
   连续服务、systemd 重启、`/ready` 重入和 session epoch。对
   `video-replica-api@8002` 重复。禁止把单个 `/live`、Nginx 静态页或仅进程重启
   视为通过；两轮都必须证明单在线仍成立。
3. **Worker 故障**：一次只杀一个 `video-replica-worker@N`，并按 crash 时点分别
   记录。对无 lease 的空闲 worker 可执行
   `systemctl kill --kill-who=main --signal=SIGKILL video-replica-worker@N` 后验证替代
   worker 正常领取后续任务。对已完成 claim、任务已持久化为 `SUBMITTING` 的受控任务
   注入同一故障后，等待 lease expiry/sweeper；原任务必须进入
   `SUBMISSION_UNCERTAIN` 人工对账，替代 worker 只能处理后续任务，绝不能重新提交
   原任务或强行完成它。每轮比较任务 lease、Provider idempotency key、`RESERVE` 终态
   和钱包账本；必须证明同一业务动作没有重复付费或重复 Provider POST，不得用新建
   幂等键掩盖重试。
4. **PG HA failover**：仅通过数据库供应商/DBA 的受控 failover 操作切换主备，应用
   不得拥有 failover 凭据。记录主库失效、API `/ready` 摘除、写入恢复、候选时窗与
   迁移 head；恢复后用专用 backup service 运行
   `cd /opt/video-replica/app/server && sudo -u postgres env \
   VIDEO_REPLICA_PG_BACKUP_SERVICE_FILE=/etc/video-replica/backup.pg_service.conf \
   VIDEO_REPLICA_PG_BACKUP_SERVICE=video_replica_pitr \
   python -m scripts.pitr_recovery_facts verify --manifest /受控路径/label.json`，
   其中两个变量必须与受控 `pitr.env` 一致，不能使用 application DSN。逐笔核对
   100 条恢复事实，并复核单在线、账本和队列。数据库 RTO 目标为
   `RTO <= 5 分钟`；已确认资金事务目标为 `RPO=0`。任一指标达不到时，记录实际值和
   明确降级，不能以“自动切换成功”放行。
5. **依赖临时失败**：COS、ZPay 与付费 Provider 不接真实账号。只在隔离 staging 的
   `受控 stub` 注入 timeout、5xx 和提交后断连；记录首次请求的幂等键、状态机、重试
   次数、最终 `SETTLE` 或 `RELEASE`，证明故障恢复仍复用同一幂等键。不得执行真实
   ZPay、COS 或付费 Provider 调用；这些真实联合链只在 T40 获得明确授权后进行。
6. **收口证据**：保存候选 SHA、脱敏拓扑、每次注入/恢复的时间线、LB/worker/DB
   状态、100 条 verifier 摘要、idempotency 对照、RPO/RTO、T37 fired/resolved 外部
   接收记录和 No-Go/回滚结论。不能只保留截图、命令历史或本地 journal；证据模板为
   `docs/evidence/T39-EVIDENCE.md`。所有不变量均通过且独立复核完成前，不得提升
   `STAGING_VERIFIED`。

## 7. 滚动发布

> 以下通用步骤要求新旧接口兼容。从 053 升到含管理端重构和 054 的版本时，
> 使用第 7.1 节的维护窗口，不能直接让新旧 API 混合承接请求。

1. 冻结候选 SHA、配置版本和回滚 SHA，确认数据库迁移的前后兼容窗口。
2. 在唯一迁移主机执行迁移；失败立即停止发布，不启动新进程。迁移安排在低峰：
   CHECK 重建等 DDL 要拿 `ACCESS EXCLUSIVE` 锁，高峰排队会让全部钱包请求跟着
   等待。`deploy/postgres/migrate.sh` 与 `customer-git-rollout.sh` 的迁移步已默认
   带 `lock_timeout=5s`（`VIDEO_REPLICA_MIGRATION_LOCK_TIMEOUT` 可调，设 0 关闭），
   拿不到锁快速失败，低峰重跑即可。注意两条路径读该变量的位置不同：migrate.sh
   读宿主 shell 环境；rollout 在容器内展开，需写入 compose env file
   （`/etc/video-replica/customer.env`），宿主 export 不生效。
3. 若本次候选改动了 `deploy/systemd/` 下任何单元（含 timer），必须重装并
   daemon-reload——滚动发布只替换代码，不会自动更新 systemd 单元，漏掉这步的
   变更会静默不生效（实例：2026-09-22 #181 给 `video-replica-maintenance.service`
   新增微信掉单兜底 `reconcile_pending_native_orders` / `close_expired_native_orders`
   两条 ExecStart，全仓文档当时未记载重装要求）：

   ```bash
   install -m 0644 deploy/systemd/video-replica-maintenance.service /etc/systemd/system/
   systemctl daemon-reload
   # timer 下个触发周期自动生效；要立即验证可手工跑一次其中的 reconcile 命令。
   ```

4. 从 LB 摘除 `api@8001`，停止、替换代码、执行 bootstrap、启动并等待
   `/ready=200`，再加入 LB；随后对 `api@8002` 重复。
5. Worker 每次只替换一个：停止后等待当前任务退出或进入受控恢复状态，启动
   新版本并观察领取/结算，再继续下一个。
6. 最后替换静态制品并 reload Nginx：`client/dist`（客户）与 `client/dist-admin`
   （管理）两个目录一起替换，不能只换一个——两者出自同一 SHA 的
   `npm run build:all`，混用不同 SHA 的制品会让管理端调用客户壳未提供的接口。
   替换后验证客户页正常、`/admin` 由 dist-admin 提供且资源路径带 `/admin/` 前缀。
7. 若该环境尚无 `admin_password_credentials`，按第 2.1 节完成一次受控恢复凭据交换，
   并验证刷新页面后仍可恢复 CSRF、审计员保持只读、退出登录立即撤销会话。
8. 记录每一步时间、操作者、SHA、健康结果和异常；T37 以后同时观察 P1 告警。

### 7.1 管理端重构与 054 的同步切换（2026-09-03）

此候选同时改变客户列表响应结构、管理写契约和首帧确认参数。发布前冻结同一
代码 SHA 对应的 API/Worker 镜像、`client/dist`、`client/dist-admin` 和客户 NSIS 包；记录每项 SHA-256、
实际 API 地址、数据库 revision 与回滚版本。旧 `8bd0374` 服务端/Web 产物及更早
桌面包不能代表新候选；CI 中指向 `staging.example.invalid` 的 NSIS 包只用于构建验证。

1. 先在隔离环境验证备份可恢复、053→054 升级和下述回滚边界，再进入维护窗口。
   暂停新任务提交和管理写入，等待在途任务完成或进入已登记的受控恢复状态；
   付费提交未确认结果时不得强杀、重试或重建任务。
2. 从入口摘除旧 API，保留维护页；在唯一迁移主机按第 2 节预检后迁移到
   `054_admin_free_grant_adjustments`。失败则停止切换，不开放新功能。
3. 更新全部 API 和 Web 静态文件，逐一验证 `/ready`。Worker 按第 7 节有序替换，
   核对当前任务状态后再接新任务；旧新首帧质检策略不同，不以硬停全部 Worker 代替排空。
4. 在入口恢复前检查管理员登录、客户列表分页、归档码回看、审计筛选及只读权限。
   同步刷新管理页面，避免缓存旧写契约。免费发放和首帧人工放行的写入验收先在
   隔离环境完成；生产写入按发布授权执行并保留账务/审计证据。
5. 新服务端就绪后再发放匹配的客户包并启用新版首帧确认功能。新桌面的
   `allow_unverified` 请求不兼容旧 API；新版产生的 `quality_override` 也不被旧 API
   的生成检查认可。仅部署服务端不会更新已安装的 Tauri 客户端。

054 的额度列和乘法 CHECK 使用 PostgreSQL `integer`。管理调账数量必须在
`1..2147483647`，且数量 × 有效单价不得超过 `2147483647`；免费发放同样受此
数据库计算边界约束，但订单金额始终为 0。另需保证钱包增加后不超过字段上限。
越界请求返回 `400 / ADJUSTMENT_VALIDATION_FAILED`，不生成订单、CHARGE 或调账审计。

## 8. 回滚

- 应用回滚：先停止继续滚动，从 LB 摘除异常版本，恢复上一 SHA 的 API/Worker
  与静态文件，再逐节点执行 bootstrap 和 `/ready` 验证。静态文件回滚必须同时恢复
  `client/dist` 与 `client/dist-admin`（CW-019 起两者是同一 SHA 的两个独立制品），
  只回滚其中一个会让管理端与客户壳跨 SHA 混用。
- 配置回滚：恢复上一密钥/配置版本时保留仍在有效窗口内的旧 key version；
  不得为恢复服务而打开本地存储、Fake Provider 或 SQLite。
- 数据库回滚：优先使用前向修复。只有在迁移明确可逆、已验证备份且进入维护窗
  后才执行 downgrade；不得在新旧应用仍并行写入时回退 schema。
- 资金、单在线、fencing、Provider 提交或账本不变量任一失败，立即停止扩大，
  进入 R3/No-Go，保留审计事实并执行 T39 故障处置，禁止直接改余额或删账本。

**054 特别边界：** 一旦存在零金额管理订单或 `FREE_GRANT` 审计行，迁移会明确拒绝
降回 053，并保留 revision 和账务数据。不得删改审计、关闭触发器、强制 stamp 或
改写已发布的 054 来绕过保护；导出数据不等于可以删除历史。优先前向修复。
保留 054、只回退应用仍须用真实旧镜像在隔离环境验证启动入口和业务数据兼容性，
包括 `quality_override`。旧源码没有 revision 硬拦截不代表回滚已通过。

## 9. 灰度边界

T36 只建立 staging 与滚动发布能力。真实 ZPay/COS/付费 Provider 在 T40 经
明确授权后执行；10 码与 100 码灰度分别属于 T41；只有 T42 签署
`PRODUCTION_GO` 后才能称为正式开放。

## 10. 资金异常处置与退款 SOP（BILL-04 冻结前的人工单例流程）

> 背景：客户钱包没有自动退款通道（BILL-04 未冻结）。在退款/开票/税务流程
> 冻结之前，一切资金回退都必须走本节的人工单例流程，禁止直接 UPDATE 余额
> 或删除账本行（026/039 约束与 T23 红线）。

1. **错扣/多扣（任务计费异常）**：先查 `generation_tasks` 与
   `wallet_transactions`，确认 `RESERVE` 是否已有终态行。终态任务的悬挂
   `RESERVE` 由每日 maintenance 的
   `scripts.reconcile_dangling_billing_reservations` 自动补齐 SETTLE/RELEASE；
   `SUBMISSION_UNCERTAIN` 任务必须人工核对 Provider 结果后按 T39 口径处置，
   绝不能自动重发付费 POST。
2. **客户诉求退款**：管理员经审计调账通道（T23 `admin_adjustment`，双确认 +
   来源单 + 幂等键 + 真实 actor）做反向调账，来源单填写工单/沟通记录编号；
   银行卡/支付渠道实际退付款项在 ZPay 商户后台人工操作，两笔事实以来源单
   编号对齐并留档。
3. **对账**：每次人工处置后运行 `scripts.reconcile_customer_billing`，
   确认账本差额为零；处置记录（含原因、审批人、凭证）归档入当期运维证据。
4. **升级**：单笔异常金额超过运营授权阈值时，暂停该客户后续充值并上报
   业务负责人；同类异常一个观察窗内出现两次即触发 T37 `billing` 告警复核。
