# 超管与加盟商分销架构设计

日期：2026-09-17
分支：`feat/admin-rbac-superadmin-20260917`
工作树：`.worktrees/ADMIN-RBAC-SUPERADMIN-20260917`

## 1. 背景与目标

现有后台是单租户结构：一套全局定价、一个全局客户池、`admin` 角色拥有全部配置权（含 API 服务商密钥与上游成本）。

本次改造把它变成**两级分销平台**：

```
上游 API 服务商（即梦 / 可灵 / TikHub …）
   ↓  upstream_cost   真实成本，仅超管可见
超级管理员（平台方）
   ↓  wholesale_price 批发价，加盟商看到的"成本"，需真实付费
管理员（加盟商）
   ↓  retail_price    零售价，加盟商自行设定
终端客户（购买积分）
```

两条资金流：终端用户付款**直接进加盟商**的收款渠道；加盟商**预充值**给平台方，按批发价扣减。

两级利润：加盟商看 `retail − wholesale`；平台方看 `wholesale − upstream`，且分加盟商统计。

### 已确认的决策

| 决策项 | 结论 |
|---|---|
| 加盟商之间数据可见性 | 完全隔离（真多租户） |
| 加盟商看到的成本 | 超管设定的批发价，不可自行修改 |
| 终端用户收款归属 | 直接进加盟商，加盟商再充值给平台方 |
| 加盟商欠费策略 | 余额不足时拒绝新任务，已入队任务正常完成 |
| 超管账号形态 | 可有多个，系统阻止删除最后一个 |
| 爆款视频库 | 按租户隔离 |
| 交付方式 | 一步到位，不分期 |
| 隔离机制 | PostgreSQL 行级安全（RLS） |

### 本设计做出的默认假设

以下未经单独确认，按唯一合理解释处理，如需调整请在评审时指出：

1. **存量数据归属**：现有全部客户、项目、素材、钱包归入平台自营租户 `tenant_platform`，平台方可继续直接经营。
2. **超管跨租户读取**：超管会话不设 `app.current_tenant`，改用具备 `BYPASSRLS` 的数据库角色，或策略中显式放行 `current_setting('app.is_super_admin') = 'true'`。实现时二选一，测试覆盖必须证明超管能读全部、加盟商读不到他人。
3. **employee / auditor 归属**：这两个角色隶属于某一租户，继承该租户的隔离边界；不存在跨租户的 employee。
4. **批发价粒度**：按「租户 × 计费科目」设定。未单独配置时回落到平台默认批发价。

## 2. 角色与租户模型

### 2.1 角色扩展

```python
# server/app/auth.py
Role = Literal["employee", "admin", "auditor", "customer", "super_admin"]
```

`admin` 语义变更：从"平台管理员"变为"加盟商主账号"。这是破坏性变更，存量 `admin` 用户在迁移中归入 `tenant_platform`。

### 2.2 新增表

```sql
tenants(
  id              TEXT PRIMARY KEY,
  name            TEXT NOT NULL,
  status          TEXT NOT NULL,          -- active | suspended | closed
  owner_admin_user_id TEXT,               -- 加盟商主账号
  created_at, updated_at
)

tenant_wallets(
  tenant_id       TEXT PRIMARY KEY REFERENCES tenants(id),
  balance_fen     BIGINT NOT NULL DEFAULT 0,
  credit_limit_fen BIGINT NOT NULL DEFAULT 0,   -- 透支额度，默认 0
  updated_at
)

tenant_wallet_transactions(
  id, tenant_id, type, amount_fen, balance_after_fen,
  ref_type, ref_id, reason, actor_user_id, created_at
)

tenant_recharge_orders(...)   -- 加盟商向平台方充值，走平台方收款渠道
```

`users` 表新增 `tenant_id TEXT NULL`：`super_admin` 为 `NULL`（跨租户），其余角色非空。

### 2.3 守卫层

现有守卫在 `server/app/admin_auth_routes.py` 末尾：

```python
AdminReader = Annotated[AdminActor, Depends(get_admin_actor)]    # admin + auditor
AdminWriter = Annotated[AdminActor, Depends(get_admin_writer)]   # 仅 admin
```

`get_admin_actor` 每次请求都重查用户的角色与激活状态，是天然的租户上下文注入点。

改造：

1. `AdminActor` 增加 `tenant_id: str | None` 字段，由 `get_admin_actor` 从 `users` 表一并读出。
2. 新增 `SuperAdminReader` / `SuperAdminWriter`，仅 `super_admin` 通过。
3. `get_admin_actor` 在建立数据库会话时设置 `app.current_tenant`（超管走假设 2 的放行路径）。

好处：100+ 条下游路由不需要改签名即可获得租户上下文。

## 3. 三级价格

### 3.1 费率表扩展

`server/app/admin_rate_routes.py:67` 现有 `kind: Literal["upstream_cost", "external_price"]`，扩展为三档：

| kind | 含义 | 维度 | 写权限 | 读权限 |
|---|---|---|---|---|
| `upstream_cost` | 真实上游成本 | 全局 | super_admin | 仅 super_admin |
| `wholesale_price` | 批发价 | 按租户 | super_admin | super_admin + 该租户 admin（只读） |
| `retail_price` | 零售价 | 按租户 | 该租户 admin | super_admin + 该租户 admin |

数据迁移：现有 `external_price` 全部转为 `tenant_platform` 的 `retail_price`；`upstream_cost` 保持不变。同时为每个计费科目生成平台默认 `wholesale_price` 种子值（初始等于 `upstream_cost`，由超管上线后调整）。

### 3.2 定价读取签名变更

`server/app/customer_pricing.py:48` 的 `read_pricing(conn)` 当前无租户参数，是全系统单一定价来源。

改为 `read_pricing(conn, *, tenant_id: str)`。**所有调用点都必须显式传入租户**，漏改会导致按他人价格计费。该函数没有安全默认值可用，因此不提供默认参数——让漏改在类型检查阶段就暴露。

### 3.3 利润口径

- 加盟商视角：`retail_price − wholesale_price`
- 平台方视角：`wholesale_price − upstream_cost`，按租户分组，并提供全局汇总

加盟商首页（`client/src/admin/OverviewPage.tsx`）的「今日成本 / 今日毛利 / 利润率」三张卡保留，成本来源从 `upstream_cost` 切换为该租户的 `wholesale_price`。

## 4. 两级结算

### 4.1 资金流 A：终端用户 → 加盟商

现有链路（`wallet_routes.py` / `recharge_routes.py` / `billing_meter.py` / `usage_billing.py`）结构不变，两处调整：

- 价格来源：全局定价 → 租户 `retail_price`
- 收款渠道：`PaymentSettingsSection` 的支付配置从全局改为**按租户**存储（每个加盟商填自己的微信商户号 / ZPay 凭据）

注意：支付渠道配置是本次改造中**唯一不收归超管**的敏感配置，因为收款主体是加盟商本人。

### 4.2 资金流 B：加盟商 → 平台方

全新链路。加盟商在后台充值，走平台方的收款渠道，入账到 `tenant_wallets.balance_fen`。

### 4.3 两段独立扣费（不联动）

两级扣费**不在同一事务内联动**，而是两段各自独立的记账：

**第一段 — 加盟商侧**
加盟商充值进 `tenant_wallets`，平台按该租户的实际用量、以 `wholesale_price` 计价扣减。这段记账独立提交，不参与终端用户的业务事务。

**第二段 — 终端用户侧**
终端用户消费时只扣自己的积分（`retail_price`），走现有 `billing_meter.py` / `usage_billing.py` 链路，**逻辑完全不变**。

两段之间不做同步回滚。安全性由 4.4 的预付费闸门保证：加盟商必须先有余额才能让任务进来，所以不会出现加盟商长期负债。

这样做的收益：

- 现有终端用户计费链路零改动，只换价格来源（租户 `retail_price`）
- 不存在"用户扣了、加盟商没扣"的跨账本回滚问题
- 加盟商侧扣减可以批量、可以重算、可以对账修正，不影响线上任务

代价与处置：加盟商侧扣减存在短暂延迟窗口，期间余额显示略高于实际。用预付费闸门 + 幂等键兜住：每笔扣减以计费操作 ID 为幂等键，重放不产生第二次扣减，漏记可通过对账作业补记。

### 4.4 欠费闸门

任务提交前校验：

```
tenant_wallets.balance_fen + credit_limit_fen >= 预估 wholesale_price
```

不足则返回 402，错误码 `TENANT_BALANCE_INSUFFICIENT`，面向终端用户的文案为"服务暂不可用，请联系客服"（不暴露加盟商欠费事实）。

已入队任务不受影响，正常执行完成——这部分批发成本由平台方先行垫付，通过 `credit_limit_fen` 之外的实际负余额体现，供超管催收。

## 5. 租户隔离

### 5.1 表分类

98 张表分四类：

**A 类（60 张）— 加 `tenant_id` + RLS**

`projects` `assets` `generation_tasks` `generation_batches` `generation_batches_new` `generation_task_operations` `characters` `character_personas` `character_versions` `character_assets` `character_asset_reviews` `character_generation_tasks` `character_sheet_tasks` `character_reference_selections` `person_identities` `project_main_characters` `oral_tasks` `oral_avatars` `oral_voices` `oral_consents` `studio_drafts` `studio_saved_scripts` `studio_material_preferences` `studio_notification_preferences` `wallets` `wallet_transactions` `wallet_credit_conversions` `recharge_orders` `activation_codes` `activation_code_batches` `activation_code_activations` `activation_code_deliveries` `activation_code_events` `activation_code_exports` `customer_api_keys` `customer_devices` `customer_discounts` `customer_unit_prices` `customer_credit_pricing` `customer_session_state` `device_pairing_requests` `first_frame_tasks` `analysis_tasks` `script_from_audio_tasks` `script_rewrite_tasks` `source_frame_tasks` `publish_records` `publish_accounts` `publish_browser_accounts` `admin_adjustments` `viral_videos` `viral_video_favorites` `viral_video_visibility` `viral_collection_batches` `viral_collection_members` `viral_collection_charges` `billing_operations` `billing_credit_lots` `billing_evidence` `billing_tariffs`

判定规则：凡承载客户数据或加盟商经营数据的表都归入 A 类。实施时以迁移脚本的实际清单为准，新表默认按此规则归类。

**B 类（9 张）— 平台全局，仅超管**

`provider_settings` `operation_cost_rates` `operation_cost_records` `runtime_settings` `viral_runtime_controls` `external_call_logs` `h3_provider_accounts` `h3_provider_task_accounts` `tenants` 自身

`h3_provider_task_accounts` 虽然带 `task_id` 指向租户任务，但它是平台账号池的调度绑定表，账号本身是平台资源，因此不加 `tenant_id`。

**C 类 — 双视角**

`audit_logs`：加 `tenant_id`，加盟商只看本租户，超管看全部。

**D 类（28 张）— 基础设施，不隔离**

不承载业务数据的支撑表，保持现状：会话与凭据（`admin_sessions` `admin_password_credentials` `internal_access_tokens` `customer_session_events`）、幂等与证据（`admin_write_idempotency` `customer_idempotency_envelopes` `customer_authorization_evidence` `customer_fencing_write_evidence`）、安全与运维（`security_auth_failures` `security_rate_limit_counters` `ops_alert_state` `admin_device_events`）、内容寻址与缓存（`content_objects` `versions` `viral_script_cache` `viral_fetch_state`）、迁移元数据（`alembic_version`）等。

A/B/C/D 四类合计覆盖全部 98 张表。实施时逐张核对，任何一张未归类即视为迁移未完成。

对每张 A 类表：

```sql
ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <t> FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON <t>
  USING (tenant_id = current_setting('app.current_tenant', true));
```

`server/app/db_pg.py` 的 `pg_transaction()` 是统一的连接入口，在此一处注入 `SET LOCAL app.current_tenant`。

超管路径按假设 2 处理。

RLS 的价值在于：即便应用层漏写一处过滤条件，数据库层仍然兜底，泄漏不可能发生。

### 5.3 存量数据迁移

1. 建 `tenants` 表并插入 `tenant_platform`
2. A 类表加 `tenant_id`，回填为 `tenant_platform`
3. 加 `NOT NULL` 约束
4. 启用 RLS

分步进行以保证大表可回滚（遵循项目的数据库迁移安全规范：加 nullable → 回填 → 加约束）。

## 7. 测试防线

三道，缺一不可：

1. **扩展静态权限矩阵**（`server/tests/test_cw027_admin_permission_matrix.py`）
   - 每条新路由必须显式分类为 super / admin / 自助
   - 每张 A 类表必须已启用 RLS，未启用即失败

2. **跨租户泄漏矩阵**（新建）
   - 对每张 A 类表：用租户 A 的会话查租户 B 的数据，断言 0 命中
   - 覆盖读、写、更新、删除四类操作
   - 覆盖超管反向用例：超管必须能读到全部租户

3. **两段扣费各自正确**（新建）
   - 终端用户侧：扣减金额等于该租户的 `retail_price`，任务失败时回滚（现有行为不变）
   - 加盟商侧：扣减金额等于该租户的 `wholesale_price`，以计费操作 ID 为幂等键，重放不产生第二次扣减
   - 对账：给定一批计费操作，加盟商侧扣减总额必须等于按批发价重算的结果（允许延迟，不允许错账）
   - 欠费闸门：余额不足时新任务被拒，已入队任务仍完成

## 8. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| `read_pricing` 调用点漏改 | 按他人价格计费，资损 | 移除默认参数，让类型检查暴露；定价相关路由全量回归 |
| 加盟商侧扣减漏记或重复 | 少收或多收加盟商的钱 | 以计费操作 ID 为幂等键 + 对账作业按批发价重算校验 |
| RLS 策略配置遗漏某表 | 跨租户泄漏 | 静态矩阵断言每张 A 类表已启用 RLS |
| 超管账号被盗 | 密钥、成本、全部租户数据一次性失守 | 本设计不含二次验证；建议后续单独立项，当前至少保证超管操作全量进审计日志 |
| 存量数据迁移失败 | 上线阻塞 | 分步迁移（nullable → 回填 → 约束），每步可独立回滚 |
| `admin` 角色语义变更 | 存量管理员行为改变 | 迁移中全部归入 `tenant_platform`，行为与改造前一致 |
