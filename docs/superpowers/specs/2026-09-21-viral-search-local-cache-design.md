## 1. 背景与问题

当前爆款视频模块（2026-09-13 上线的 VIRAL-CLOUD-MEDIA 链路）存在三个结构性问题：

1. **成本结构重**：运营每日/每周采集 → 全量强制云归档原分辨率视频（5–20MB/条）到平台 COS，平台长期持有并承担播放流量。
2. **无自由搜索**：页面只能浏览运营采集的批次，搜索仅为客户端本地过滤（`${item.title}${item.author}` 内存匹配）。
3. **无本地缓存**：客户无法沉淀视频文件；源站播放 URL 仅几小时有效，过期即不可用。

业务方向调整（2026-09-21 用户确认）：**让用户自己搜索关键词；视频缓存在客户本地；服务器只存"内容和数据"；不实现在线播放；运营不再做视频采集。**

## 3. 目标与非目标

**目标**
- 平台视频存储成本归零（复刻/文案素材经平台过程性持有、直传供应商，随任务清理，不积累存量）
- 平台播放流量归零（视频播放只在客户本地发生）
- 搜索成为内容唯一入口；内容数据（元数据 + 封面 + 文案）持续沉淀在服务器
- 客户获得可靠的本地视频资产（缓存后可反复播放/提取/复刻，不受源站 URL 过期影响）；**缓存按源站默认分辨率，非压缩档**

**非目标（明确不做）**
- 平台侧在线播放（服务器不提供视频流给播放器）
- 运营侧视频采集（每日/每周采集调度取消）
- 服务端长期保留任何视频文件
- 平台承担视频下载流量（下载发生在客户端 ↔ 源站之间）

## 4. 总体架构

```
┌───────────────────── 客户端（桌面端为主）─────────────────────┐
│  搜索框 → 结果卡片（封面 / 标题 / 数据，不自动播放）            │
│  本地缓存区： {app_data}/viral-cache/{platform}/{video_id}.mp4 │
│    + 本地索引（文件名即索引：文件存在 = 已缓存）                 │
│  播放：video_id 命中本地索引 → <video src=本地文件>；未命中不可播│
│  提取文案 / 拆解 / 复刻：上传已缓存文件（直达平台 API）          │
└──────────────────────────────────────────────────────────────┘
        │ 下载：客户端 ↔ 源站（TikHub 返回的直链），不过平台
        │ 上传：复刻/文案素材经平台直传供应商（秘塔支持直传），
        │       平台仅过程性持有，随任务清理（不留云存储）
┌───────────────────── 平台服务器（轻资产）─────────────────────┐
│  搜索代理（TikHub douyin / wechat）＋按次计费                    │
│  内容池 viral_videos（元数据 + 封面 cover_key 长期副本）         │
│  发现记录 viral_search_discoveries（user_id, keyword, 日期）     │
│  文案服务：ASR/拆解结果（共享缓存，跨客户复用）                   │
│  复刻直传：上传 → 平台过程临时区 → 直传秘塔 H3（multipart）      │
│  运营视图（内容池/每日汇总/推荐位挑选）+ 客户视图（我的发现）     │
└──────────────────────────────────────────────────────────────┘
```

**职责边界**
- 客户端独担：视频文件的下载、存储、播放、上传发起
- 服务端独担：搜索调用、内容落库、封面归档、发现记录、文案结果、计费、视图
- 唯一例外：复刻/文案时素材经平台"过路"（过程性持有，随任务清理，不落持久存储）

## 5. 服务端设计

### 5.1 数据模型

**沿用 `viral_videos`（内容池）**——迁移 070 已建表，字段完整（platform, video_id, title, author, cover_url, cover_key, duration_ms, likes..., play_url, audio_url, native_json）。
- 搜索命中 → upsert（刷新互动数据 / 封面 / 播放直链）
- 封面机制直接复用：搜索时归档封面 → `cover_key` → `GET /api/viral/covers/{platform}/{video_id}`（无需登录，长期可显示，Cache-Control 7 天）——**满足"封面必须显示"**
- 新增使用场景：`play_url` 语义扩展为“下发给客户端做本地缓存的源站直链”（时效性由客户端下载时机保证）；**直接下发源站默认播放地址，不做档位挑选**（§5.2）

**新增 `viral_search_discoveries`（发现记录）**

```
viral_search_discoveries
  id            TEXT PRIMARY KEY
  user_id       TEXT NOT NULL          -- 搜索的客户
  keyword       TEXT NOT NULL          -- 搜索词
  platform      TEXT NOT NULL          -- douyin / wechat
  video_id      TEXT NOT NULL          -- 命中的视频
  search_date   TEXT NOT NULL          -- YYYY-MM-DD（"每天"维度）
  searched_at   TEXT NOT NULL          -- 精确时间（同一天多次搜索取最新）
  UNIQUE(user_id, keyword, platform, video_id, search_date)
```

- 客户视图：`我的发现`（按 search_date 分组）→ "用户每天搜索到的视频"
- 运营视图：每日汇总（关键词热度、内容池增量、推荐位候选来源）

**不建的表（9-19 版设计的重资产部分作废）**
- ~~`viral_media_objects` / `viral_media_references`~~（共享视频对象库——视频不再上云，无对象可共享）
- ~~`local_viral_cache`~~（服务端记录客户端缓存——客户端自己管理，服务端不需要也不应知道）

**过程临时区（复刻/文案素材）**
- 定位：复刻/文案链路的"文件过路区"——不是对象存储、不是持久业务资产、不做业务登记
- 载体：平台服务器过程临时目录（按任务 ID 隔离）；任务完成/失败即清理，另有 24 小时兜底清理
- 部署备注：worker 与 API 同机或共享卷部署直接可用；多实例无共享卷时退化为"COS 临时前缀 + 生命周期删除"（实现兜底，非默认）
- 合规：过程临时文件不属于业务主存储门禁（CW-031）约束范围（其约束的是持久业务资产）

### 5.2 搜索接口（新增）

```
POST /api/viral/search
body: { keyword, platform: "douyin" | "wechat", cursor?: string }
resp: {
  items: [{
    platform, videoId, title, author, authorAvatar, verified,
    coverUrl,            -- /api/viral/covers/{platform}/{video_id} 长期副本
    durationMs, likes, comments, shares, collects,
    publishedAt, publishedDisplay,
    playUrl,             -- 抖音：源站默认播放地址；视频号：null（下载前经 refresh 解析）
    audioUrl,
    hasCopy              -- 服务端批量查 viral_script_cache：true=文案已就绪（点击提取瞬间返回）
  }],
  cursor: string | null,
  hasMore: bool,
  billing: { charged: true, unit: "viral_search" }
}
```

- 服务端行为：校验额度 → 调 TikHub → normalize（复用 `viral_tikhub.py`）→ upsert 内容池（playUrl 直取源站默认播放地址，选择逻辑改造见 §5.5）+ 归档封面 → 写发现记录 → 批量填充 `hasCopy`（查 `viral_script_cache`）→ 返回
- 分页：视频号走 cursor（每页 10 条，TikHub 单次返回量）；抖音为单次批量返回（`douyin_search` 无分页参数，返回即全部）
- **每页数据量 = API 单次返回量**（与"翻页即缓存"对齐，见 §6.2）
- 计费：每次搜索请求（首搜 + 每次翻页）各扣一次 `viral_search` 项（2026-09-22 确认）
- 错误：额度不足 402；上游失败 503（复用现有错误码风格）；结果为空正常返回空列表

**配套接口**
- `POST /api/viral/search/refresh`（新增）：入参 `{platform, videoId}`，解析/重新解析该视频的可下载直链；响应 `{ url, decodeKey }`
  - 抖音：复用 `viral_link.py` 解析（现状仅支持抖音/小红书，**不含视频号**）
  - 视频号：调 TikHub `wechat_video_detail` 取 `full_url` + `decode_key`（取参方式同媒体管线：`native_json` 的 `export_id` / `object_nonce_id`；两者必须同批使用）
  - 用途：视频号搜索结果为 `playUrl=null`，缓存下载前必须经此解析；亦作下载失败/URL 过期的刷新兜底
- `GET /api/viral/copy?platform=&videoId=`（新增）：**共享文案瞬间命中**——查 `viral_script_cache`（关联键 platform + video_id），命中即返回 `{ text, updatedAt }`；未命中返回空（客户端转入提取链路）。命中路径不触发下载/上传/ASR，不产生费用
- `GET /api/viral/discoveries?date=YYYY-MM-DD`（新增）：客户"我的发现"（按天）
- 运营侧（管理端接口，沿用现有 admin 模式）：
  - `GET /api/admin/viral/discoveries?date=...` 每日汇总
  - 推荐位挑选：改造现有精选接口——不再要求 `storage_uri`（见 §5.4）

### 5.3 文案服务（提取文案 / 拆解）

- 客户端上传已缓存视频 → 平台过程临时区 → **服务端先分离音轨**（ffmpeg 抽音频为 M4A，复用 `script_from_audio.py` 现有 `extract_audio` 机制）→ **用音频送 ASR 转写**（2026-09-22 确认）→ 临时区随任务清理
- **文案回填与“与视频的关联”**（2026-09-22 确认）：
  - 转写成功 → **写入 `viral_script_cache`**（既有 PG 表，主键 `platform + video_id`——这就是“和视频的关联”，无需新表）→ 客户端将文案**回填到该视频的文案区**（详情页 / 卡片展开）
  - **瞬间命中**：任何用户点击“提取文案”前先查 `GET /api/viral/copy`——命中即瞬间显示（不下载、不上传、不抽音轨、不重复付费）；即现有 `_lock_script_cache` 复用机制的服务端轻量读路径
- 音频输入 ASR 两条路（**不再上传对象存储临时对象**——现状 `put_object` 到云存储取签名 URL）：
  - 短音频（时长 ≤5 分钟且编码后 ≤10MB）：`data:audio/mp4;base64` inline 直传（`prepare_audio_input` 现有能力，不经任何存储）
  - 长音频：平台过程临时区的临时签名 URL（复用 `viral_routes.py` 的 HMAC 签名文件路由风格；依赖平台对供应商公网可达，现状生产 API 即公网域名）供 ASR 拉取；音频归过程临时区管理（随任务清理 + 24h 兜底）
- 跨客户复用与去重并发沿用现有机制（`viral_script_cache` 行锁 + producer task 追踪，避免重复付费提交）
- 提取文案不受 15 秒限制（保持现状：15 秒仅约束复刻，见 `viral_import_routes.py:256-257`）
- 拆解（复刻第一步）沿用现有分析链路，素材来源改为过程临时区（平台读取后提交供应商）

### 5.4 复刻链路改造

现状：H3 生成要求输入媒体是 HTTPS 公网 URL（`generation.py:583-584` 校验，秘塔从公网拉取）→ 迫使参考视频必须先归档到云存储。

**秘塔 H3 支持文件直传（2026-09-22 确认）**，链路改为全程文件流、不经云存储：

```
客户端（本地缓存文件 / 用户上传文件）
  → POST /api/viral/replica/uploads（multipart 直达平台 API）
  → 平台过程临时区（任务级隔离）
  → 拆解：平台读取临时区文件提交拆解供应商
  → 首帧：平台读取临时区文件提交首帧供应商（现有 multipart 能力，first_frames.py）
  → H3 生成：multipart 直传秘塔（新增直传模式）
  → 生成完成 → 过程临时区清理
```

- 上传方式：multipart 直达平台 API（"我们的 API 直接上传文件"）；不再使用"客户端直传对象存储"（upload-intent）模式
- **实现注意**：`generation.py` 现有 `_h3_request_media_urls_are_https` 是 URL 模式的门禁——新增直传模式时保留 URL 模式兼容（存量任务、其他入口），直传模式走文件字段并复用相同角色契约校验（`_validate_h3_reference_request` 等）
- 成品（H3 输出）为正式业务资产，正常落存储（客户资产，不属过程临时区）

## 6. 客户端设计（桌面端为主，Tauri 客户云工作台）

### 6.1 搜索页（爆款页重构）

- 顶部：搜索框（主入口）+ 平台切换（抖音 / 视频号，继承现有双平台 Tab）
- 快捷词：现有 5 分类（建房预算 / 户型设计 / 施工避坑 / 庭院案例等）转为**一键搜索词**（点击即以其为关键词搜索）；存量内容的分类字段保留展示
- 结果列表：现有卡片复刻（封面 + 标题 + 作者 + 互动数据 + 时长）；分页加载（"加载更多"或页码，按平台能力）
- **翻页即缓存**：每页数据到达后，客户端自动将该页全部视频加入下载队列（§6.2）
- 卡片状态：**细进度条**（缓存中实时百分比）+ 角标（`排队中` / `缓存中` / `已缓存` / `缓存失败（可重试）`）
- 下载管理面板（新增）：缓存队列总览——每条一个进度条（速度/大小/状态）+ 总体进度 + 重试/暂停/打开目录（§6.2）
- “文案已就绪”标记：`hasCopy=true` 的卡片显示标记；点击“提取文案”瞬间展开（§5.3）
- "我的发现"：按天分组展示自己搜索到的内容（服务端 discoveries）
- 存量批次浏览入口移除；存量内容并入内容池（可通过搜索 / 推荐位触达）

### 6.2 本地缓存（核心新增）

**Rust 侧新增模块 `viral_cache.rs`**（桌面壳现无 fs 插件，延续自建 Tauri 命令风格，见 `lib.rs`）：

| 命令 | 作用 |
|------|------|
| `viral_cache_ensure(platform, video_id, url, decodeKey?)` | 入队下载（多线程分段）；`.part` 临时名下载完成后原子重命名；进度事件；含 `decodeKey` 时下载后解密（视频号） |
| `viral_cache_status(items)` | 批量查询缓存状态（页面角标） |
| `viral_cache_list()` | 已缓存列表 + 磁盘占用 |
| `viral_cache_delete(platform, video_id)` | 单条删除 |
| `viral_cache_clear(scope)` | 批量清理（全部 / 按平台 / 超出容量部分） |
| `viral_cache_open_folder()` | 打开缓存目录 |

**缓存目录与索引**
- 路径：`{app_data_dir}/viral-cache/{platform}/{safe(video_id)}.mp4`
- `safe()`：video_id 可能含 `/`（视频号 opaque ID）→ URL-safe 转换
- **索引 = 文件系统本身**（文件存在即已缓存）；元数据一律从服务端内容池接口获取；不引入本地数据库
- 元数据 sidecar（可选）：`.json` 记录下载时间/来源 URL（用于诊断），非必需

**下载（多线程）**
- **单文件多线程分段**：HTTP Range 并发拉取（默认 4 连接/文件，可调）；分片写临时文件 → 按序合并 → 原子重命名为正式文件；源站不支持 Range（无 `Accept-Ranges`）时退化为单连接流式
- **队列并行**：多视频同时下载（默认并发 3，可调）；失败自动重试 ≤2 次（重试前调 `/search/refresh` 刷新直链）
- **默认分辨率**：下载直取源站默认地址，不做档位挑选、不采用压缩低清档（§5.2 / §5.5）；视频号 `full_url` 即原片
- **视频号解密（本地完成）**：`full_url` 下载所得为加密数据（仅前 128 KiB），**在客户端本地解密**（Rust 实现 ISAAC64，不把原始文件交由服务端处理）——Python `viral_decrypt.py` 已有已知答案向量，Rust 单测复用同向量交叉验证；解密幂等：已是 `ftyp` 头则原样；`decode_key` 与 `full_url` 必须同批获取
- 直链过期兜底：刷新仍失败 → 该条标记“缓存失败（可重试）”，不阻塞其他条目
- 源站防盗链：Rust 下载请求携带常规 UA/Referer，字段实现时实测（§10 风险）
- HLS 兜底：若某平台返回 m3u8（非 mp4 直链），客户端不做分片合并，改走服务端代取一次（允许的少量例外）——实现时按实测数据决定

**进度可视化（进度条）**
- 进度事件：Rust 下载模块经 Tauri event 推送（`viral-cache-progress`：video_id / 已下载字节 / 总字节 / 速度 / 状态）；分段下载进度 = 各分片已下载字节合计
- 卡片级：细进度条实时刷新（事件驱动，不轮询）；完成后切换为“已缓存”角标
- 面板级：下载管理面板（§6.1）逐条进度条 + 总体进度；失败显示原因与“重试”入口

### 6.3 播放

- 详情页：查本地索引
  - 命中 → 本地文件播放（Tauri asset 协议 `convertFileSrc`；CSP 的 `media-src` 已预置允许 `asset:`，实现时需在 `tauri.conf.json` 显式启用 `assetProtocol` 并配置缓存目录 scope）
  - 未命中 → 显示"未缓存，无法播放"占位 + "缓存到本地"按钮（触发下载，完成后原地可播）
- 列表卡片：不播放（无自动预览）
- **服务器永不参与播放**（不生成任何播放用签名流）

### 6.4 提取文案 / 拆解

- 入口：详情页按钮 + 卡片快捷按钮（延续现有）
- 流程（先查缓存，再走链路）：
  1. **查服务端共享缓存**（`GET /api/viral/copy`）→ 命中：**瞬间显示**（不下载视频、不扣 ASR 费用；`hasCopy` 标记的卡片即此路径）
  2. 未命中 → 检查本地缓存 → 未缓存则**先自动下载（进度条，§6.2）** → 上传文件至平台（过程性持有，随任务清理）→ **服务端先分离音轨（ffmpeg 抽音频）→ 音频送 ASR 转写**
  3. 结果**回填该视频文案区**（详情页 / 卡片展开）+ 服务端写入共享缓存（`platform + video_id` 关联）→ 下一个用户点击提取瞬间命中
- 结果持久化在服务端共享缓存（跨设备、跨客户复用）

### 6.5 复刻

- 入口一：本地已缓存视频（选择"用此视频复刻"）
- 入口二：上传本地文件（通用）
- 均走：客户端上传 → 平台过程临时区 → 拆解（直传供应商）→ 首帧（直传供应商）→ H3 生成（multipart 直传秘塔，§5.4）→ 临时区清理
- 生成成品为正式资产（正常存储）

### 6.6 缓存清理策略（默认值，review 可调）

- 容量上限：默认 **20 GB**（到达上限时提示并触发清理）
- 自动清理：LRU（按最后访问时间），**收藏视频永不自动删除**（收藏列表来自服务端）
- 手动：缓存管理页（列表 / 占用排序 / 单删 / 批量删 / 打开目录）

### 6.7 Web 端降级（非桌面）

- 可用：搜索、内容展示、封面、我的发现、推荐位
- 不可用：本地缓存 / 播放 / 复刻（提示"请使用桌面客户端"）
- 提取文案：桌面端为主；Web 端降级为服务端临时拉取（源站直链 → 过程临时区 → ASR），属允许的少量例外

### 6.8 推荐位（首页精选）

- 运营从**内容池**挑选（数据 + 封面，不依赖视频文件）
- 首页精选卡片 → 详情页（内容 + 封面）
- 播放/文案/复刻遵循同一规则：需先缓存

## 10. 风险与兜底

| 风险 | 影响 | 兜底 |
|------|------|------|
| 源站直链防盗链 / 客户端直下失败 | 缓存失败 | Rust 携带 UA/Referer 实测；失败 → `/search/refresh` 刷新直链重试；仍失败 → 服务端代取（有限例外） |
| 直链仅几小时有效 | 翻页后延迟下载失败 | "翻页即缓存"天然在 URL 新鲜期内启动下载；队列内置刷新重试 |
| 某平台仅提供 HLS（m3u8） | 客户端下载复杂 | 先实测；必要时该平台走服务端代取兜底 |
| 视频号 video_id 含 `/` | 文件名/路径安全 | `safe()` 转换 + 服务端精确匹配（沿用 covers 路由校验逻辑） |
| H3 提交新增直传模式需改动 generation.py | 影响面广 | 仅新增 multipart 直传路径，保留原 HTTPS URL 模式兼容；对接后先行小流量验证 |
| 抖音默认地址为 HEVC/ByteVC1 私有编码 | WebView2 本地播放兼容性 | 实现时实测默认地址编码与播放效果；若不可播，兜底改取兼容编码档（保留“选档”为降级路径） |
| 视频号客户端解密 | Rust 需复刻 ISAAC64 算法 | 与 Python `viral_decrypt.py` 共享已知答案向量交叉验证；解密失败兜底服务端代取一次 |
| ASR 长音频走平台临时 URL | 依赖平台对供应商公网可达 | 现状生产 API 即公网域名；本地开发环境走短音频 inline 路径 |
| 过程临时区的部署依赖 | 多实例时文件可见性 | 同机/共享卷直接可用；不满足时退化为 COS 临时前缀 + 生命周期删除 |
| 存量已归档视频处置 | 成本残留 | 停止新增；只读保留观察一个周期后再评估清理 |
| 本地磁盘失控（大缓存量客户） | 体验问题 | 容量上限 + LRU + 收藏保护（§6.6） |

## 12. 测试策略

**服务端（pytest）**
- 搜索接口：正常返回 / 上游失败 / 额度不足 / 封面归档 / 内容池 upsert 去重 / 发现记录按天去重
- 直链解析：playUrl 直取默认播放地址 / `/search/refresh` 双平台路径（抖音 `viral_link.py`、视频号 `wechat_video_detail`）
- 计费：每次搜索（含翻页）扣费一次；采集计费确无触发路径
- 文案音轨分离：ffmpeg 抽音轨 + ASR 两路（短音频 inline / 长音频签名 URL）
- 文案缓存：瞬间命中不触发 ASR / 未命中转提取 / 成功后写入 `viral_script_cache` / 第二用户复用不重复付费
- 复刻直传：H3 multipart 直传提交链路（对接验证）+ 原 URL 模式兼容回归；过程临时区随任务清理
- 精选门槛：改造后封面替代 `storage_uri` 的放行/拦截

**客户端（vitest + Rust 单测）**
- 缓存索引：文件名映射 / `safe()` 转换 / 状态查询
- 多线程下载：分段 Range 并发 / 合并顺序 / 不支持 Range 的退化路径 / 失败重试 / 直链刷新联动
- 视频号解密：ISAAC64 已知答案向量（与 Python `viral_decrypt.py` 同向量）/ 幂等重放
- 进度事件：分段进度聚合 / 完成切换“已缓存”/ 失败重试联动
- 清理策略：LRU / 收藏保护 / 容量上限触发

**端到端（桌面端）**
- 搜索 → 翻页 → 自动缓存（进度条）→ 本地播放 → 提取文案（首提全链路 + 第二用户瞬间命中）→ 复刻（真实网络，标记 integration）
