# 退款闭环立项书：负向调账与退款 SOP 对齐

> 立项日期：2026-09-22　基线：`origin/main @ 02ac56a4`
> 性质：**决策材料**。本文件不定义资金规则，只把"已拍板的 SOP"与"代码能做到的事"之间的差额摆清楚，供拍板。
> 来源：`docs/管理端代码综合评审报告-2026-09-12.md` P1-2、`docs/前后端页面功能与接口匹配梳理-2026-09-18.md` §5 P0 行。

## 0. 结论（TL;DR）

评审报告把退款记作"闭环四层皆缺（接口/状态机/入口/回滚）"，但**产品侧其实已经拍过板**：`docs/客户版部署与灰度手册.md` §10（BILL-04 冻结前的人工单例流程）明确规定——**不做自动退款通道，退款走"管理员审计调账反向调账 + ZPay 商户后台人工退付"双事实对齐**。

问题在于：**这条 SOP 的第 2 步在代码里执行不了**。审计调账通道只接受正向加秒，账本 CHECK 约束也只允许正向 `CHARGE`，所以"反向调账"这一半事实根本落不了账。

因此本立项要做的事，**不是新建退款状态机**（那属于 BILL-04 冻结后的议题），而是：

> **把 SOP §10 第 2 步变成可执行、可审计、可对账的动作** —— 即受控放开负向调账。

这是一个**收敛得很小的改动**（1 个迁移 + 1 处路由校验 + 1 处前端 + 对账口径），不是"四层皆缺"的大工程。

## 2. 硬约束证据（三层，逐层 file:line）

负向调账当前在三个层次上被同时禁止：

**第一层 — 路由校验只允许正数**
`server/app/admin_customer_routes.py:426`
```python
if not 1 <= body.credits <= 2147483647:
    raise _http(400, "ADJUSTMENT_VALIDATION_FAILED", "Credits must be between 1 and 2147483647.")
```

**第二层 — 账本 CHECK 约束要求 CHARGE 必须为正**
`server/migrations/versions/022_internal_billing.py:160-179`
```python
sa.CheckConstraint("type IN ('CHARGE', 'RESERVE', 'SETTLE', 'RELEASE')",
                   name="ck_wallet_transactions_type"),
...
"(type = 'CHARGE' AND available_delta > 0 AND reserved_delta = 0 ..."
```
即 022 原文里 `CHARGE` 的 `available_delta` 被钉死为 `> 0`。

**但 022 不是当前口径**——`20260913T0630_account_credit_operations.py:69-82` 已把该约束演进为：
```python
"type IN ('CHARGE', 'RESERVE', 'SETTLE', 'RELEASE', 'CONVERSION')"
...
_OLD_SHAPE + " OR (type = 'CONVERSION' AND available_delta <> 0 AND reserved_delta = 0 "
"AND recharge_order_id IS NULL AND task_id IS NULL AND "
"oral_task_id IS NULL AND billing_round IS NULL)"
```

这条对本次立项是**利好**：`CONVERSION` 分支已经允许 `available_delta <> 0`，即**负向、且不挂订单/任务/账单轮次的账本形状在库里已经有了先例**。新增 `REFUND` 类型可以直接照抄这个形状分支，不需要发明新的记账形态，迁移风险显著低于"从零设计负向账本"。

`server/app/control_routes.py:60` 的 Python 侧 `TransactionType = Literal["CHARGE", "RESERVE", "SETTLE", "RELEASE", "CONVERSION"]` 与当前 CHECK 一致（此前"漂移"的判断是拿它对比已被取代的 022 原文，不成立，已作废）。

**第三层 — 钱包余额不得为负**
`server/migrations/versions/022_internal_billing.py:75`
```python
sa.CheckConstraint("available_credits >= 0", name="ck_wallets_available_nonnegative"),
```

**并列的语义错位：枚举里已经有"退款"，但只能加钱**
`server/app/admin_customer_routes.py:118-126` 的 `SOURCE_DOCUMENT_TYPES` 含 `REFUND_APPROVAL`、`LEDGER_CORRECTION`；前端也真的把它们做成了下拉选项：
- `client/src/admin/AdjustmentsPage.tsx:109` — `<option value="REFUND_APPROVAL">退款审批</option>`
- `client/src/admin/SessionsPage.tsx:28-29` — `"REFUND_APPROVAL"`

运营在界面上选"退款审批"，**结果只能给客户加钱**。这是当前最危险的一点：动作与标签方向相反，且落库后 audit 里留的是"退款"字样。

**订单侧同样没有退款态**
`server/migrations/versions/022_internal_billing.py:101` `ck_recharge_orders_status` 未含 `REFUNDED`；`server/tests/test_postgres_migrations.py:1126` 显式断言 `rejected(21, status="REFUNDED")`——**给订单写 REFUNDED 是被测试钉死的非法状态**。

调账当前是"造一笔 PAID 充值单 + 一笔 CHARGE 流水"来完成的（`admin_customer_routes.py:520-560`），所以它的**正向性是从订单语义里继承来的**，不是孤立的校验。

## 3. 方案对比

| | 方案 A：受控负向调账（推荐） | 方案 B：新建退款状态机 | 方案 C：维持现状 |
|---|---|---|---|
| 做法 | 新增账本类型 `REFUND`，放开 `REFUND_APPROVAL`/`LEDGER_CORRECTION` 走负数，余额下限护栏 | 订单加 `REFUNDED` 态 + 退款单实体 + 审批流 + 网关退款接口 | 不动代码，退款只在 ZPay 后台做 |
| 与 SOP §10 关系 | **完全对齐**（SOP 就是这么写的） | 超出 SOP，等同提前做 BILL-04 | 与 SOP 冲突（SOP 第 2 步要求反向调账） |
| 工作量 | 小（1 迁移 + 路由 + 前端 + 测试） | 大（状态机 + 对账 + 网关） | 零 |
| 风险 | 中（动了资金账本，但有 CHECK + 审计 + 对账三重护栏） | 高（引入新的资金状态机） | **资金台账与系统账不一致**，`reconcile_customer_billing` 差额永远对不平 |
| 建议 | ✅ 本期做 | ⏳ 与 BILL-04 冻结一并议 | ❌ 不可取 |

**为什么方案 C 不可取（关键）**：SOP 要求"每次人工处置后运行 `reconcile_customer_billing` 确认差额为零"。如果账本侧不能反向记账、而 ZPay 侧实际退了钱，**两边永远差一笔**，对账脚本会持续报差额，SOP 自己的验收条件无法满足。也就是说，**不放开负向调账，SOP 就无法闭环**。

## 4. 方案 A 实施拆解（建议）

1. **迁移**（链尾追加，不改既有迁移）
   - `ck_wallet_transactions_type` 增加 `'REFUND'`；形状分支**照抄 `20260913T0630` 的 `CONVERSION` 分支**：
     `type = 'REFUND' AND available_delta < 0 AND reserved_delta = 0 AND recharge_order_id IS NULL AND task_id IS NULL AND oral_task_id IS NULL AND billing_round IS NULL`
     （`CONVERSION` 用的是 `<> 0`；`REFUND` 建议收紧为 `< 0`，正向补偿继续走既有 `CHARGE`）
   - 同步 `TransactionType` Literal（`control_routes.py:60`）与前后端词典 `vocabulary.ts`
   - **红线：只加约束分支，不改既有五类的形状**；迁移必须可降级，降级守卫照 `20260913T0630:85-109` 的写法（存在该类型行即拒降）
2. **路由**
   - `admin_customer_routes.py:426`：按 `source_document_type` 分流——`REFUND_APPROVAL`/`LEDGER_CORRECTION` 允许负数，其余维持 `>= 1`
   - 负向时**不建 `recharge_orders` 行**（退款不是充值；且 `ck_recharge_orders_status` 无退款态），改为在 `admin_adjustments` 侧留痕
   - 余额下限护栏：拒绝会把 `available_credits` 打成负数的调账（对应第三层 CHECK），返回明确 400 码
   - 保留既有四件套：双确认 + 来源单 + 幂等键 + 真实 actor + 同事务审计
3. **前端**
   - `AdjustmentsPage.tsx` / `SessionsPage.tsx`：选中 `REFUND_APPROVAL` 时金额输入允许负数，并明确提示"此为账本反向记账，实际退付在 ZPay 后台办理"
   - 调账记录列表需能区分正负（当前 `AdjustmentListItem.credits` 为 `number`，需确认展示口径）
4. **对账**
   - `scripts/reconcile_customer_billing.py`：把 `REFUND` 纳入口径（当前有 `PG_ONLY_TABLES`/`PG_ONLY_COLUMNS` 豁免清单，需一并核对）
   - 跑通"退款一笔 → 差额为零"的验收
5. **测试**：迁移形状约束正反例、路由负向放行/越界拒绝、余额下限拒绝、审计字样、auditor 只读

## 5. 需要拍板的决策点

| # | 决策点 | 备选 | 影响 |
|---|---|---|---|
| D1 | 退款额度上限 | 不得超过该客户**累计实付**（建议）／不得超过当前可用余额／不设上限 | 决定 §4.2 的护栏写法 |
| D2 | 余额下限 | 不允许打成负数（建议，与既有 CHECK 一致）／允许透支 | 决定 §4.2 是否需额外授权分支 |
| D3 | 负向流水用**新类型 `REFUND`** 还是**复用 `CONVERSION`** | 新增 `REFUND`（建议，语义清晰、不动历史积分链路）／复用 `CONVERSION`（零迁移，但语义错位且会污染历史积分转换的口径） | 决定要不要加迁移 |
| D4 | 订单侧要不要 `REFUNDED` | 本期不加（建议，退款不产生充值单）／加 | 决定是否推翻 `test_postgres_migrations.py:1126` |
| D5 | 是否需要二次审批人 | 单人 + 审计（现状）／双人复核 | 决定前端是否加审批步骤 |

## 6. 验收口径（DoD）

1. 运营在管理端选中"退款审批"做一笔负向调账后：账本出现 `type='REFUND'` 且 `available_delta < 0` 的行；审计可见真实 actor、来源单号、原因、幂等键
2. `reconcile_customer_billing` 在该笔处置后**差额为零**
3. 会打成负余额的调账被拒（400，明确错误码），DB CHECK 为纵深兜底
4. auditor 调用被拒（`AUDITOR_READ_ONLY`），前端只读收敛
5. 既有正向调账行为零回归；迁移可降级且降级后既有四类形状不变
6. 全量门禁绿

## 7. 影响面与红线

- **触碰资金账本**，是全项目风险最集中的区域：必须保留四件套写契约、同事务审计、`FOR UPDATE` 状态机，禁止直接 UPDATE 余额或删除账本行（026/039 约束与 T23 红线）
- **迁移链冻结**：只允许链尾追加，不改既有迁移文件
- 本立项**不涉及**真实退付通道（ZPay 侧仍是人工），不改变"BILL-04 未冻结"的现状表述
