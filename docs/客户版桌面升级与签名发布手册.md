# 客户版桌面升级与签名发布手册

本手册覆盖客户云桌面端（Windows NSIS）的签名发布与**自动更新**全流程。
被 `scripts/release/build-customer-signed-release.ps1` 与
`client/src-tauri/customer-installer-hooks.nsh` 引用；实机升级验收（CW-046）
与真实旧数据切换（CW-051）以本手册的验收清单收尾。

## 架构一览

- 唯一签名发布入口：`npm run release:customer`（本地签名机执行，fail-closed）。
- 升级分发：客户服务器 nginx 静态托管，`https://<域名>/downloads/customer-cloud/stable.json`
  是当前版本清单；`<version>/` 目录内存放安装包、`.sig`、校验和与发行记录。
- 客户端（Tauri 官方 updater 插件）：启动静默检查（每天最多一次，发现新版本才弹窗），
  用户中心顶栏可手动「检查更新」；下载后先校验 minisign 签名再静默安装，提示重启生效。
- 双重签名：updater 的 minisign 签名（防下载通道篡改）+ 安装包本身的 Authenticode
  签名（Windows 信任链）。两把钥匙相互独立，都只存在于签名机。

## 一、一次性准备

### 1. 生成 updater 密钥对（每套环境一次）

在签名机上：

```powershell
npm run tauri --workspace client -- signer generate -- -w C:\keys\customer-updater.key
# 提示设置密码：务必设置，并把密码与私钥分开保管
```

- **公钥**（命令输出里 `dW50cnVzdGVk…` 那串）：替换
  `client/src-tauri/tauri.customer.conf.json` 里
  `plugins.updater.pubkey` 的 `REPLACE_WITH_UPDATER_PUBLIC_KEY` 占位值，提交入库。
- **私钥**：只留在签名机（配合密码管理器保管），不进仓库、不进 CI、不打日志。
- 私钥一旦泄露：生成新密钥对并入库新公钥，之后**发布的下一个版本**起改用新钥；
  已经装出去的旧版本只认旧公钥，无法被新钥签的版本自动升级——这是换钥的固有代价，
  也是私钥保管必须严格的原因。

### 2. 服务器开通升级通道（每台客户服务器一次）

nginx 已有模板：`deploy/nginx/customer.conf.example` 中
`location = /downloads/customer-cloud/stable.json` 与
`location ^~ /downloads/customer-cloud/` 两个块。把 alias 目录对齐到
`$VIDEO_REPLICA_SITE_ROOT/downloads/customer-cloud`
（默认 `/www/wwwroot/video.zszhj.cn/downloads/customer-cloud`），然后：

```bash
nginx -t && systemctl reload nginx
```

发布脚本 `deploy/customer-desktop-release.sh` 随仓库正常 git 发布即可到达服务器。

## 二、每次发版

1. **bump 版本**：五处版本号（`tauri.conf.json` / 根与 client 的 `package.json` /
   `package-lock.json` / `Cargo.toml` / `server/pyproject.toml`）保持一致，
   发布脚本会再校验一次。
2. **在签名机上设置环境变量**：

   | 变量 | 说明 |
   | --- | --- |
   | `VIDEO_REPLICA_RELEASE_SIGN_THUMBPRINT` | Authenticode 证书指纹（已有流程） |
   | `VITE_API_BASE_URL` | 客户云正式域名，如 `https://video.zszhj.cn` |
   | `TAURI_SIGNING_PRIVATE_KEY` | updater 私钥内容（一行） |
   | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥密码（设了密码就必填） |
   | `VIDEO_REPLICA_RELEASE_EXPECTED_SIGNER` | 可选，签名者主题子串校验 |

3. **构建**（更新日志会展示在客户端升级弹窗里）：

   ```powershell
   npm run release:customer -- -ReleaseNotes @"
   本次更新：
   - 消费记录一条任务一行
   - 修复历史记录显示
   "@
   ```

   产物在 `dist-release/customer-cloud/<version>/`：
   `<安装包>.exe`、`<安装包>.exe.sig`、`stable.json`、`SHA256SUMS.txt`、
   `release-manifest.json`。
4. **上传**整个版本目录到服务器任意临时路径（scp/rsync 均可），然后在服务器上：

   ```bash
   sudo deploy/customer-desktop-release.sh --release-dir /tmp/2.5.0
   ```

   脚本会校验 SHA256 与清单一致性，经 staging 原子落位版本目录并切换
   `stable.json`，最后回读线上清单确认生效；任何一步失败都会自动恢复旧清单。
5. **验收**：找一台已安装客户端的机器 → 用户中心顶栏「检查更新」→ 应弹出新版本
   与更新日志 → 立即更新 → 进度条走完 → 重启后「关于/页脚」版本号已更新。

## 三、回滚

```bash
sudo deploy/customer-desktop-release.sh --rollback <旧版本号>
```

注意两点：

- 回滚只影响**尚未升级**的客户端。已经自动升到坏版本的机器因为
  `allowDowngrades: false` 不会自动降级；修复方式是发一个**更高版本号**的修复版。
- 每次切换都会留档 `stable.json.<版本>.bak`，回滚即恢复其中一份；
  `stable.json` 当前指向的版本目录与它上一个版本目录不要删除。

## 四、第一个自动更新版本的特殊性

带自动更新能力的**第一个**版本（本功能上线后的那次发版）需要存量用户
**手动下载安装一次**——之前装出去的版本没有更新程序。此后所有版本均可自动升级。
首次发布时建议把官网/直发渠道的安装包同步替换为该版本。

## 五、故障排查

| 现象 | 排查 |
| --- | --- |
| 客户端提示检查失败 | 服务器 `curl -fsS https://<域名>/downloads/customer-cloud/stable.json` 应返回 JSON；404 多为 nginx location 未配或 alias 路径不对 |
| 提示已是最新 | `stable.json` 的 `version` 必须高于客户端当前版本号才会触发更新 |
| 下载后安装失败/签名校验失败 | 该版本必须用与客户端内置公钥**同一对**密钥签署；换过密钥对或漏设 `TAURI_SIGNING_PRIVATE_KEY` 都会出现（后者发布脚本会直接拒绝出制品） |
| 升级后旧数据/登录丢失 | NSIS hook 的旧版归档在 `%LOCALAPPDATA%\短视频复刻客户云工作台\legacy-backup`；凭据（DPAPI 信封）在安装目录之外，正常升级不受影响 |
| 发布脚本拒绝出制品 | 按报错补齐环境变量；公钥仍是占位值时也会拒绝（防止发出永远无法自升级的包） |
